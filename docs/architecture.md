# Architecture

> **Implementation status:** This document describes the target architecture and illustrative
> patterns, not completed features. The current stack is an early API prototype with no UI app.
> REST now has a memory trip store and minimal demo routes; GraphQL has a deterministic prototype.
> The showcase will use a static Next.js UI, REST-owned persistence, and optional cloud providers;
> live credentials and deployments are not prerequisites for the local demo.

This is the orientation document for the whole stack: what the product does, which of the four
repositories owns which responsibility, and — the part worth reading even if you never touch this
codebase — why a REST domain service *and* a GraphQL aggregator in front of it is a deliberate
pattern rather than an accidental extra hop. Read it before your first change to any repo, and come
back to it when you are deciding where a new piece of behavior belongs.

---

## The product: "Wander"

Wander is a collaborative, agentic trip planner. A user describes a trip in natural language — "4
days in Lisbon, mostly food and live music, hate early mornings, budget-ish" — and the system turns
that into a day-by-day itinerary that streams in as it is generated, can be refined by conversation,
and can be shared by link.

The domain is deliberately chosen to earn the tools the stack demonstrates:

| Product need                                | Technique it justifies                              |
| ------------------------------------------- | --------------------------------------------------- |
| Itinerary appears progressively as generated | GraphQL subscriptions over SSE                      |
| One trip view needs many domain records     | DataLoader batching across a REST fan-out           |
| Preferences persist per person              | Authentication and a per-user data partition        |
| Weather, places, events all shape a plan    | Multiple independent external providers             |
| "Make day 2 more relaxed"                   | A streaming LLM in the request path                 |
| Public share links                          | Caching, CDN, and an unauthenticated read path      |

Every one of those external dependencies is optional at runtime. The whole product runs on
deterministic mock providers with no accounts, no keys, and no network access — see
[the provider pattern](./patterns/provider-pattern.md).

## The three tiers

```
                     react-ui (Next.js, urql, Tailwind, Sentry)
                                     │ GraphQL (http + SSE)
                     graph-api (Yoga, DataLoader, OTel)
                       │                    │
     providers/ (llm, weather, places, events)   HTTP + Zod client
                                                     │
                                           rest-api (Bun, Hono, OpenAPI, OTel)
                                                     │
                                           providers/ (store, auth)
                                                     │
                                           DynamoDB   Cognito
```

### `rest-api` — the domain service

Owns the *nouns*: trips, days, activities, activity candidates, preference profiles, share links. It
is a plain CRUD service — Zod schemas are the single source of truth for validation, TypeScript
types, and the generated OpenAPI document. It talks to persistence and identity through its own
provider ports (`store`, `auth`) and knows nothing about GraphQL, about the UI, or about the LLM.

The test of whether something belongs here: *would this rule still be true if the product had no
planning feature at all?* "A trip has between one and thirty days" belongs here. "A trip's itinerary
is generated by fanning out to a weather provider" does not.

### `graph-api` — the aggregation and orchestration layer

Owns the *verbs* that span sources. It composes one client-shaped graph out of several upstreams:
domain records from `rest-api`, forecasts from a weather provider, candidate venues from a places
provider, live listings from an events provider, and the itinerary itself from an LLM. Orchestration
lives in `src/services/`, as pure functions that take a bundle of provider ports and perform no I/O
of their own; resolvers are thin adapters that unwrap arguments and hand off.

This tier is also where the two hardest runtime concerns live: streaming (the planner emits chunks
that the subscription republishes to subscribers) and N+1 avoidance (DataLoader collapses per-field
domain reads into batched upstream calls).

### `react-ui` — the experience

Owns presentation and interaction: the planning form, the live-streaming itinerary view, the
day-by-day board with pin/swap, the share view, and MDX-rendered documentation pages. Data access is
confined to container components using a typed urql client whose documents and hooks are generated
from a checked-in schema snapshot. The UI never calls `rest-api` directly — one client-facing
endpoint means one place to enforce authorization, shape responses, and instrument.

### `graph-rest-react-stack` — the doc hub and orchestration repo

Owns everything that is *about* the other three rather than *inside* them: this `docs/` tree, the
Docker Compose topology, the shared-foundation CDK app, and the deploy orchestration script. It
carries no application code.

## Why REST *and* GraphQL

The most common objection to this shape is that the GraphQL layer is a pass-through — that
`react-ui` could call `rest-api` directly and delete a network hop. That objection is right for a
single-source CRUD app and wrong here, for four reasons worth being able to articulate.

**1. They answer different questions.** REST is at its best when the unit of exchange is a
*resource* with a stable identity and lifecycle: `PUT /trips/{id}` is a complete, cacheable,
idempotent statement about one thing. GraphQL is at its best when the unit is a *view*: "this
screen needs a trip, its days, each day's activities, the forecast for each day, and any events
near the pinned activity." Expressed against a resource API that is one request per node and a
render-blocking waterfall; expressed as a graph it is one request whose shape the client chooses. A
service that tries to be both grows endpoints named after screens — `/trips/{id}/full-view-v2` —
and those endpoints rot in step with the UI.

**2. They have different rates of change.** The domain model changes when the business changes.
Client query shapes change every time a designer moves a card. Separating them means UI iteration
does not touch the service that owns the data, and domain changes do not require a UI release to
deploy. This is the same argument as separating a database schema from the queries run against it.

**3. Fan-out needs somewhere to live.** Weather, places, events, and the LLM are not part of the
trip domain — they are inputs to a plan. Putting them in `rest-api` would make the domain service
depend on four vendors and turn a simple `GET /trips/{id}` into a call with four failure modes and
a multi-second p95. Putting them in the UI would ship API keys to the browser and make the fan-out
serial across the public internet. The aggregation tier is where a slow, partial-failure-tolerant
composition step belongs: it can run the four calls concurrently, degrade gracefully when one
provider is down, and cache aggressively without the domain service knowing.

**4. It preserves more than one consumer.** The moment there is a second client — a mobile app, a
partner integration, a batch export, an internal admin tool — a documented, versioned, resource-
shaped API is what you want it talking to. The graph is a client-facing convenience over the domain,
not a replacement for it. Deleting `rest-api` and putting persistence directly behind the resolvers
would work today and cost you badly the first time something that is not a browser needs the data.

**When you should not do this.** If there is one client, one data source, and no external fan-out,
the second tier is real cost — an extra deploy, an extra set of types, an extra hop of latency —
for no benefit. Start with one service. Introduce an aggregation layer at the point where you catch
yourself adding a screen-shaped endpoint to a domain API, or wiring a third vendor into it.

## Cross-cutting rules that shape every tier

These are consequences of the architecture, not decoration; each has its own reference doc.

- **Ports and adapters everywhere.** Every external dependency — LLM, weather, places, events,
  persistence, auth, telemetry, error reporting — is consumed through a hand-written port interface
  with Zod-validated boundaries, one adapter file per implementation, and a registry that picks the
  adapter from a single environment variable. Business logic imports the port type and never
  branches on which adapter is live.
- **Mocks are first-class.** Every capability ships a deterministic, seeded mock. `PROVIDER_*=mock`
  is the default, so a fresh clone runs the full product offline. Mocks are not test doubles bolted
  on afterwards; they are the reference implementation of each port.
- **Config is read once per repo.** A single `src/config/env.ts` per service parses `process.env`
  with Zod and exports a frozen typed object. Nothing else reads `process.env`, so an unset variable
  fails loudly at boot rather than quietly at 3am.
- **Validation at every process boundary.** TypeScript types vanish at runtime; anything arriving
  over HTTP — a request body, an upstream response, a vendor payload — is parsed by a Zod schema
  before it is trusted.
- **OpenTelemetry is the only instrumentation API application code touches.** Traces propagate
  ui → graph → rest by W3C `traceparent`, and the backend vendor is a collector configuration, not
  an SDK import. Browser error capture through Sentry is the one deliberate exception, and it is
  still hidden behind a provider port.

## Where to put a new feature

| If the change is…                                            | It belongs in…            |
| ------------------------------------------------------------- | ------------------------- |
| A new persisted entity, or a rule about one                  | `rest-api` domain + store |
| A new external data source feeding the plan                  | `graph-api` provider      |
| A new way of combining existing sources                      | `graph-api` service       |
| A new field the client needs from data that already exists   | `graph-api` schema        |
| A new screen, state, or interaction                          | `react-ui`                |
| A new environment, container, or deploy step                 | this repo                 |

When two answers seem plausible, prefer the lower tier for *data and invariants* and the higher tier
for *composition and presentation*. Composition can be rebuilt cheaply; domain rules that leaked
upward get duplicated by the next client.
