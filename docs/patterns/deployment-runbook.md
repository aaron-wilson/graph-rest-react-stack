# One-environment deployment and recovery

This runbook describes the implemented foundation → REST → GraphQL → static UI deployment. All stacks and command paths are offline-tested; actual AWS provisioning, Docker image builds, secret injection, DNS, CloudFront delivery, Cognito login and alarm behavior remain live-unverified. The scripts do not bootstrap accounts or populate secrets. Account access and every execute command belong to the operator. They do not run from application startup or local builds.

Keep the hub, REST, graph and UI checkouts as siblings with their pinned dependencies already installed. The hub's `platform-cdk/node_modules` is the shared CDK toolchain; infrastructure scripts in each service/UI repo point to it explicitly. No infra dependency is added to an application runtime. An actual execution also needs the AWS CLI, a running Docker daemon with linux/amd64 builds, and an authorized deployment principal. `deploy-all.sh` checks CLI/daemon availability before provisioning, requires clean checkouts for execution, and never installs prerequisites. Before any account write, inspect the foundation and API/UI template diffs and cost implications: NAT, two ALBs, retained data, KMS, CloudFront and Fargate can incur charges even at idle.

Set the non-secret inputs named in `scripts/deployment.env.example` explicitly in the shell; the script never loads a file. `PLATFORM_ENV` must match the environment argument. The site origin and `DEPLOY_GRAPH_ORIGIN` are owned HTTPS origins, with regional graph and us-east-1 site certificates covering their hosts. Account, region, two AZs, Cognito domain prefix, deployment trust principal and certificate identifiers are required before a dry run. Configure only selected provider/model inputs. API keys are not script inputs: store each selected raw key as SecretString under `/wander/<environment>/v1/secrets/openai`, `anthropic` or `ticketmaster`; do not use a JSON wrapper. The foundation graph execution role has scoped access to those existing names, while REST's task role alone has table access. The deploy identity needs permissions to provision these stacks, upload to ECR/S3 and invalidate CloudFront; the foundation's deployment trust role intentionally has no broad action policy. An owner-reviewed IAM action policy and CDK bootstrap role trust are prerequisites, not an automatic administrator grant.

Bootstrap the target account/region once with the installed `platform-cdk/node_modules/.bin/cdk bootstrap aws://<account>/<region>` only after reviewing its trust and permissions. Supply suitable credentials through the normal CLI chain; never put credentials in tracked files or command-line inputs. Confirm both certificates already exist, the chosen AZs are available, and selected secret names have been populated. Bootstrap and secret population are explicit owner actions outside the script; the script only checks selected secret metadata and never reads a secret value.

From the hub, `bash scripts/deploy-all.sh <environment>` prints the deployment plan; `--dry-run` is also accepted. It prints exact commands, full source revisions and non-secret SSM placeholders without calling AWS or Docker. The placeholders are resolved by the executing script, so a printed plan is for review, not a standalone copy-and-paste substitute. `bash scripts/deploy-all.sh <environment> --execute` is the account-writing command. It deploys `Wander<environment>Foundation`, resolves `/wander/<environment>/v1` references, logs Docker into ECR through password-stdin without printing the token, and reuses existing immutable full-Git-SHA image tags. Absent tags are built for linux/amd64 and pushed. It deploys `Wander<environment>Rest` and `Wander<environment>Graph`, builds the live-config UI artifact, deploys `Wander<environment>Ui`, and publishes assets before HTML. Outputs are stored in ignored `.deployment/<environment>/` files. The complete UI export is archived there under its source revision plus a hash of its public deployment manifest; an existing archive is reused rather than overwritten. Publication uses that archived export, preserving a concrete rollback artifact even when a later build replaces `out/`. No application env file is read during synth; applications parse injected configuration at startup.

The foundation owns private subnets, ALBs, immutable image repos, Cognito, the private UI bucket, roles and encrypted 14-day API logs. UI owns the bucket's single complete TLS/OAC policy; do not add a competing foundation policy. Public DNS is deliberately not auto-managed: point the graph hostname at the foundation's graph ALB DNS and the site hostname at UI's DistributionDomain output after deployment. Site origin must match API CORS and the foundation's Cognito public client callback `<site-origin>/auth/callback/`. The public client uses authorization-code PKCE with `openid` and no client secret. UI build-time client ID, issuer and hosted domain come from foundation parameters. Graph and REST both verify the same Cognito client; REST ALB remains internal and only accepts graph task security-group ingress. Never deploy demo identity at the public API hostname.

The UI's `out/deployment.json` records the full UI revision and public GraphQL/auth identity; retain the complete export and stack/image revisions for every release. Browser settings are compiled into JavaScript, so changing runtime variables cannot update them. The orchestration path intentionally leaves Sentry and OTLP off; enabling vendor telemetry, source-map upload or paid LLMs is a separate reviewed choice. Published hashed assets are immutable and old hashes are retained. Mutable route payloads/HTML have brief caches and are invalidated after upload; publishing is not a promise of an atomic site-wide swap.

After an explicit deployment, confirm ECS desired/running task counts and healthy ALB targets, graph HTTPS `/health`, and the site direct `/docs/`, `/plan/`, `/auth/callback/` and `/share/` routes plus a missing asset 404. Sign in through Cognito, create a trip, stream/save/edit it, then load its share anonymously. Revoke the share and confirm it stops working. Restart REST and confirm the trip persists in DynamoDB. Restart GraphQL and confirm users see an interrupted generation rather than a false successful save. These are owner-operated live checks; offline test success cannot establish them. Source-map and vendor verification remain separately opt-in.

Both API stacks have one CPU alarm: greater than 85 percent for three one-minute periods. Alarms have no notification actions. On REST saturation, inspect request load, throttling and storage latency before changing capacity. On graph saturation, inspect provider deadlines, generation count and recent releases; increasing desired count above one is unsupported because generation state is in process. Graph's 0/100 deployment limits prevent overlapping tasks but cause downtime and interrupt active streams. Its 30-second ALB drain and circuit-breaker rollback do not recover lost jobs. REST's 100/200 rolling replacement uses the durable DynamoDB table.

For rollback, check out the recorded compatible clean service revisions and reuse their immutable image tags with the API stack app's explicit `API_IMAGE_TAG`; do not mutate tags or mix unknown releases. Restore the archived UI export with its original public config and manifest revision, then run `scripts/publish-static.mjs` with that artifact directory, bucket and distribution using `--execute`. The publication command retains newer hashes too, so old pages keep their assets. Rotate a provider secret in Secrets Manager only as an owner action, then replace graph tasks so ECS re-injects it; secret rotation does not update running task environments. Review circuit-breaker outcomes rather than assuming rollback completed.

For teardown, remove the UI and graph/REST service stacks first, then review foundation deletion. CDK destroy is not a complete cleanup: table, bucket, Cognito and KMS key are retained, and old ECR image tags/static assets remain. Export data, consider Cognito users and shares, delete retained resources only through a separately reviewed owner action, and verify ALBs/NAT/Fargate are gone to stop their costs. Preserve the log decryption key while encrypted logs still need reading. No teardown runs automatically, and the orchestration script has no destroy mode.

Local verification uses `bash -n scripts/deploy-all.sh`, `node --test scripts/deploy-all.test.mjs`, infrastructure typechecks/template suites and offline synthesis of all four apps with fake inputs and credential/config files disabled. The dry-run fixtures check ordering, safe defaults, revision pins, input validation and secret-value exclusion without making account or vendor calls. Docker acceptance remains a separate prerequisite when Docker is available.
