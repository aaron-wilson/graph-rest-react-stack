# Inactive check and deployment workflows

All four repositories store CI and manual deployment definitions under `.github/workflow-templates/*.yml.disabled`. GitHub does not discover these as workflows. No schedule, Dependabot configuration or active workflow is created. The templates were parsed and checked locally; no Actions run, account login or deployment was triggered. The CI definitions use read-only contents permission, timeouts, and three-day browser-report retention. Deployment requests OIDC token permission only in its explicit protected-environment job.

Each job checks out all four compatible repositories into sibling paths. Set `HUB_REPOSITORY`, `REST_REPOSITORY`, `GRAPH_REPOSITORY` and `UI_REPOSITORY` as owner/repository names, plus their `*_REVISION` full Git SHAs. A repository's own CI revision comes from the event; its manual deployment revision is the required dispatch input. Companion revisions must remain an explicitly reviewed set, not moving branches. The hub smoke definition also pins its companion revisions. Public sibling checkouts use the standard read-only token; private sibling access requires an owner-reviewed checkout credential with access to precisely those repos before activation.

Fresh CI runners explicitly install the pinned dependencies with pnpm 10.15.0 for hub/graph, pnpm 11.18.0 for UI, and Bun 1.2.21 for REST. They use Node 24, the runtime pinned by the graph/UI container recipes. Setup is part of the inactive definition and was not performed by local verification. `scripts/verify-repo.mjs <hub|rest-api|graph-api|react-ui>` invokes existing local scripts using installed binaries and prevents Bun/dotenv from reading local env files. It runs format, lint, types, tests, applicable codegen/schema/docs/images/OpenAPI drift checks, builds, infrastructure tests and fake-input synth. UI's optional `--e2e` runs the default Chrome journey; the template explicitly prepares Chrome. `scripts/check-env.mjs` checks env consumers against tracked example keys; platform/toolchain switches are excluded by name. `scripts/check-workflows.mjs` parses YAML and checks inactivity, checkout pins, permissions, timeouts and artifact retention. It is a structural checker, not a replacement for GitHub's workflow engine or actionlint.

Manual deployment definitions accept an environment and a full source revision. All sibling repos are validated before cloud credentials are acquired; the workflow invokes the implemented dry-run plan before the explicit execute step. Set non-secret variables named by `scripts/deployment.env.example` and `AWS_DEPLOY_ROLE_ARN` in the protected GitHub environment. Provider keys remain in Secrets Manager; no workflow embeds their values. Create and review the AWS OIDC trust condition for the precise repository and protected environment, and grant only the actions needed for these CDK/ECR/S3/CloudFront resources. The foundation's deployment trust role has no broad action policy by default. The job assumes an existing owner-configured role; it does not provision trust or grant administrator permissions. Each repo's deployment dispatcher releases the compatible full stack through the hub orchestration entrypoint, rather than deploying one layer against unknown companions.

The hub's separate smoke definition invokes `scripts/docker-acceptance.sh`: clean volumes, builds, Compose health gates, application smoke, a fresh writable DynamoDB volume check, table init/seed, DynamoDB Local contract, restart persistence inspection and cleanup. It uses only local emulators and mock providers. A missing Docker daemon or failed contract fails the check rather than being reported as success. New Relic, Sentry and cloud account actions are excluded.

Activation is deliberate: review action versions and repository/environment variables, configure least-privilege OIDC trust and protected-environment approvals, then copy or move one selected template into `.github/workflows/<name>.yml` and remove the `.disabled` suffix. That new commit changes the automation boundary and belongs to the owner. Until then, no CI badge or live-deployment claim is justified. Action behavior follows the upstream [checkout](https://github.com/actions/checkout), [setup-node](https://github.com/actions/setup-node), [OIDC credential](https://github.com/aws-actions/configure-aws-credentials) and [artifact](https://github.com/actions/upload-artifact) documentation; review them again at activation.
